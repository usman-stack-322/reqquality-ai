## 7. Authentication reliability follow-up — 20 October 2026

### Findings and root-cause boundary

- **Environment selection:** process environment wins, including an explicitly empty DATABASE_URL. Direct `python app.py` then reads `backend/.env.local`, followed by backend/root `.env` for unset values. WSGI imports skip `.env.local`. This workstation's direct-launch configuration intentionally selects its separate local SQLite database; imported WSGI/diagnostic configuration selects Neon PostgreSQL from `backend/.env`. This is explicit configuration, not an outage fallback. Corrected startup source reporting: local-file settings were previously misreported as inherited process environment.
- **Reproduced inaccessible database:** in the restricted execution sandbox DNS resolved three addresses, but all three socket attempts failed with PermissionError/network_access_denied in 3–4 ms. psycopg then failed with OperationalError/network_access_denied at 78 ms. No database session was created, so user lookup/password verification were never reached. Safe 503 handling does not repair this restriction.
- **Outside that sandbox:** the same configured URL passed all three TCP/TLS checks (100–126 ms TCP, TLS 1.3), established a PostgreSQL session in 1,723 ms, executed SELECT 1 in 112 ms, confirmed schema version 20261017 and required login columns in 415 ms, and executed the actual login lookup SQL in 113 ms. The diagnostic uses a nonexistent placeholder account; this does not prove valid cloud-account login. No migrations or production record writes were performed. Evidence: `audit/login-current-before.json`, `audit/login-current-network.json`.
- **Reuse/lifecycle already working:** the existing per-process pool, min_size=0/max_size=5 default, connect_timeout=3 s, checkout timeout=10 s, max_idle=60 s, max_lifetime=1,800 s, explicit return-once cleanup and shutdown/fork handling were retained. The installed psycopg connection context recognizes pool ownership and does not close a pooled socket on transaction exit. No normal-path leak or actual production pool exhaustion was reproduced. Existing zero reconnect budget allows at most the pool's immediate final retry, not an unbounded background retry chain.
- **Real gaps fixed:** sockets were not validated after idle disconnects; waiting borrowers were unbounded; query cancellations and saturation lacked the shared safe unavailable response; public pages were replaced by the session error screen after a failed background lookup; dashboard/summary rows included unused requirement bodies. Also found that psycopg_pool retains expired waiter slots until delivery: with no reachable sockets and no background reconnect chain, introducing a finite queue alone would eventually lock out recovery. Empty failed pools are now retired after timeout, while pools with active/connecting sockets remain intact. A real scheduler regression exercises 22 successive failures beyond the queue limit. These findings are distinct from the sandbox network denial.

### Remaining external actions and limitations

1. **Restricted runtime networking:** permit outbound DNS and TCP 5432/TLS to the configured provider in the actual runtime where the error occurs, or run the service outside that restriction. Direct driver failures occur quickly, but actual pooled acquisitions wait for the checkout deadline: two restricted-runtime samples failed in 10,008 / 10,009 ms (`audit/auth-sandbox-checkout.jsonl`). That explains how a blocked connection appears as a slow login before the 503. Do not reset a valid password or change DATABASE_URL to SQLite to mask a connectivity outage. This workstation's unrestricted probe is healthy; no persistent provider outage was demonstrated. Deployed runtime networking was not tested.
2. **Provider query budgets:** read-only SHOW returned statement_timeout=0, lock_timeout=0 and idle_in_transaction_session_timeout=5min. Neon/PgBouncer rejects these as startup options; session SET/RESET persistence is unsuitable for transaction pooling. A database owner should set application-role defaults, for example `ALTER ROLE <application_role> IN DATABASE <database> SET statement_timeout = '10s';` and similarly `lock_timeout = '3s'` / `idle_in_transaction_session_timeout = '15s'`, then recycle application pools and verify SHOW in fresh connections. Select budgets appropriate to migrations/exports and use a separate migration role when needed. **These defaults were not changed here; SQL and blocked-network read durations are not claimed to have a complete end-to-end application deadline.** Connection acquisition and frontend requests remain bounded; frontend cancellation does not itself cancel a server query.
3. **Cloud-user/deployment verification:** validate an authorized cloud account from the actual deployment with its configured CORS/proxy/cookies and provider role defaults. Saved local credentials belong to the separate local account, so were not sent to the cloud. No production sessions, role configuration, records or deployment were changed. Region placement/provider cold starts and real concurrency remain external performance variables.
4. **Schema setup with a transaction pooler:** current schema marker was present, so initialization was skipped. Existing session-level advisory-lock migration behavior through PgBouncer remains outside this login fix and needs a dedicated migration/direct-connection verification before a schema rollout.

Provider references: [Neon connection errors](https://neon.com/docs/connect/connection-errors) documents rejected startup options; [Neon transaction pooling](https://neon.com/docs/connect/connection-pooling#connection-pooling-in-transaction-mode) documents session-setting and advisory-lock limits and role-level alternatives.

## 8. V1 analysis implementation — 20 October 2026

### Implemented contract

The existing Gemini integration was extended rather than replaced. Inspection found no active rule-based analysis/scoring engine to remove. New analysis is exclusively a validated provider result; failures never return generated fallback content, and new risk_score remains null. Legacy numerical scores and `rule_based` provenance stay readable as historical data and are not relabeled as new AI output. Input validation, schema validation, CSRF, roles, rate limits and session controls remain in place.

- **Minimal project structure:** `projects` persists the sole supported `current` project, name, context and revision. `requirements.project_id` is additively backfilled to `current` with a singleton CHECK constraint. Existing `users.project_access` remains the access grant for that project. Unknown project IDs are denied, not silently mapped. This meets the minimal one-project analysis boundary; it does not complete the earlier proposed multi-project tenancy work.
- **Context authoring:** authenticated project members can GET `/api/project`; only SQA Admin can PATCH context with the latest integer revision and CSRF. Analyst-supplied `project_context` is ignored in favor of persisted server-owned context. Context is sent as untrusted data to the existing provider along with original text and explicit clarification answers. Admin settings expose context editing; input/detail views show context.
- **Structured response:** analysis v4 requires suggested type/explanation, ambiguities/conflicts, missing facts, a distinct clarification_questions list, testability/assumptions/edge cases, proposed refinement, acceptance criteria, qualitative risk/priority explanations and existing linked scenarios. Missing facts require questions. Prompt instructions preserve supplied actors/numbers/scope, retain contradictions as unresolved decisions and prohibit inventing business rules, deadlines or thresholds. Safety annotations flag introduced values; they do not prove semantic accuracy or replace the model.

Criterion position/link consistency still requires human review when editing criteria.
